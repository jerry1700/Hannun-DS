# 트러블슈팅 기록

> 형식: **증상 → 원인 → 해결 → 배운 것**. 코드 버그뿐 아니라 설계·협업에서 생긴 문제도 기록한다.

---

## TS-001 · 설계 문서의 입력 전제가 실제 아키텍처와 달랐다 (2026-08-27)

**증상** — STEP 0~4 설계 문서는 "BE가 기사를 DB에 저장하고 DS가 DB를 읽는다"를 전제로 BE에 DDL 공유, `duplicate_of` 컬럼 추가, pgvector 설치를 요청하는 것으로 정리돼 있었다. BE 문서를 받아보니 BE는 Kafka 토픽에 공통 기사 JSON을 발행하는 데서 끝나고, 저장(HDFS)은 DE 담당이었다.

**원인** — 설계 문서를 쓸 때 BE·DE의 역할 경계와 데이터 흐름 문서를 먼저 확인하지 않고 일반적인 구조를 가정했다.

**해결**
- 입력 인터페이스를 "DB 테이블"이 아니라 "공통 기사 JSON 파일/스트림"으로 재정의. `hannun.ingest.reader`가 JSON·JSONL·디렉토리를 읽도록 구현해 Kafka 덤프든 HDFS 익스포트든 같은 코드로 받을 수 있게 함.
- DS 자체 저장소(Gold, parquet)를 두어 BE/DE 스키마 변경과 분리.
- BE에 하던 요청을 수신자별로 재분류: 입력 관련 → DE, 서빙 DB 관련 → BE.

**배운 것** — 설계 전에 "데이터가 어디서 오고 어디로 가는가"를 그림 한 장으로 팀과 맞춰야 한다. 알고리즘 조사보다 이게 먼저다.

## TS-002 · API 스펙을 보고서야 드러난 산출물 누락 (2026-08-27)

**증상** — BE API 응답에 `score`(trending 정렬 기준)와 이슈 단위 `category`가 있는데, 설계 문서 4개 어디에도 이 두 값을 어떻게 만드는지 없었다. 또 `issueId`가 커서 페이지네이션 키로 쓰여서 "MVP는 재계산 없이 가자(C안)"는 이전 판단이 성립하지 않게 됐다.

**원인** — 설계를 "알고리즘 → 결과" 방향으로만 했고 "화면 → 필요한 데이터" 방향으로 역산하지 않았다.

**해결** — API 필드별로 "누가 만드나 / 설계에 있었나" 표를 만들어 누락(score, 이슈 category)과 승격(이슈 ID 승계 필수) 항목을 식별. WORKLOG "다음"에 출력 계약 문서 작성을 등록.

**배운 것** — 최종 소비자(API/화면) 스펙이 나오면 즉시 역산해서 산출물 목록을 갱신할 것.

## TS-003 · 마크다운 첨부 파일이 깨진 문자로 보였다 (2026-08-27)

**증상** — 설계 문서 `.md` 4개를 채팅에 첨부했을 때 `ë¸ì´ì¦` 같은 문자열로 표시됨.

**원인** — UTF-8로 저장된 파일이 Latin-1(ISO-8859-1)로 해석된 전형적인 mojibake. 첨부 경로의 인코딩 처리 문제.

**해결(우회)** — 이전에 텍스트로 붙여 넣은 내용과 요약을 기준으로 진행. 정밀 참조가 필요하면 파일을 저장소 `docs/` 아래에 두고 직접 읽는 것으로 함.

**배운 것** — 문서는 저장소에 두고 경로로 참조하는 게 가장 안전하다. 파이프라인 코드에서도 같은 이유로 `utf-8-sig`로 읽어 BOM까지 흡수하도록 했다.

## TS-004 · Python 3.14 환경에 pyarrow 없음 (2026-08-27)

**증상** — `import pyarrow` 실패. 시스템 Python 3.14에 pandas만 설치돼 있었다.

**원인** — 전역 환경에 필요한 패키지가 없었고, 전역에 설치하면 다른 프로젝트와 충돌 위험.

**해결** — `.venv` 생성 후 `pandas 3.0.5 / pyarrow 25.0.1 / pydantic 2.13.4 / pytest 9.1.1` 설치. 최신 Python이라 휠이 없을까 걱정했지만 문제없었음.

**주의** — pandas 3.0은 문자열 기본 dtype이 `str`(pyarrow 백엔드)로 바뀌었다. Gold 저장소는 pandas dtype 추론에 의존하지 않고 `GOLD_SCHEMA`(pyarrow)로 고정해 이 영향을 차단했다.

## TS-005 · 모노레포로 옮기자 데이터 폴더 이름이 파트 디렉토리와 겹쳤다 (2026-08-27)

**증상** — 팀 저장소가 루트에 `back/ data/ front/ infra/`를 둔 모노레포였다. 프로젝트를 `data/` 아래로 옮기니 우리가 쓰던 `data/samples`, `data/gold`가 `data/data/samples`처럼 되고, CLI 기본값·테스트 픽스처·문서 경로가 전부 그 이름을 참조하고 있었다.

**원인** — 원격 저장소 구조를 보기 전에 로컬에서 폴더 이름을 정했다. TS-001과 같은 종류의 실수다.

**해결** — `samples/`(커밋)와 `gold/`(무시)로 바꾸고, Grep으로 참조 8곳(gitignore, CLI 기본값, conftest, 샘플 스크립트, README, CODE_STYLE, 티켓 문서, GIT_CONVENTION)을 고쳤다. 실행 기준 디렉토리를 `data/`로 명시했다.

**배운 것** — 저장소에 올릴 코드는 첫 줄을 쓰기 전에 원격의 디렉토리 구조를 먼저 본다. 경로 문자열이 코드·테스트·문서 여러 곳에 흩어지기 전에.

## TS-006 · 커밋 작성자가 다른 팀원 이름으로 올라갔다 (2026-08-27)

**증상** — 티켓 99 커밋 5개가 다른 팀원의 이름과 이메일로 원격에 푸시됐다.

**원인** — 첫 커밋 전에 `git config user.name`, `user.email`을 눈으로 확인하지 않았다. 공용 실습 PC라 한 컴퓨터에 여러 사람의 설정과 흔적이 남아 있었고, 원격 이력에 있던 팀원 계정을 본인 것으로 착각해 저장소 로컬 설정에 넣었다.

**해결** — 잘못 넣은 로컬 설정을 지우고 본인 계정을 다시 명시한 뒤, `git rebase origin/data/dev --exec "git commit --amend --no-edit --author='jedabin <jedabin@naver.com>'"`로 5개 커밋의 작성자·커미터를 교체하고 `git push --force-with-lease`. 본인만 쓰는 feat 브랜치라 강제 푸시가 가능했고, MR을 만들기 전이어서 리뷰 링크가 깨질 일도 없었다.

**배운 것** — 저장소를 처음 잡을 때 `git config user.email`을 저장소에 명시하고, 첫 커밋 직후 `git log -1 --format='%an <%ae>'`로 확인한다. 공용 PC에서는 전역 설정을 믿지 않는다. 강제 푸시는 MR 전, 혼자 쓰는 브랜치에서만.
