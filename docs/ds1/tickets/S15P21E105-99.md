# S15P21E105-99 · 공통 기사 JSON 입력 변환 · Gold 저장

| 항목 | 내용 |
|---|---|
| 상태 | 구현 완료 (로컬 parquet). HDFS 연동·실데이터 검증 대기 |
| 코드 | `src/hannun/ingest/` — schema.py · reader.py · gold.py · pipeline.py · cli.py |
| 테스트 | `tests/test_schema.py`, `tests/test_gold.py` (21개) |
| 관련 티켓 | 100(전처리 — Gold 위에 정제 컬럼 추가), 10(STEP 1 — Gold를 읽음) |

## 1. 티켓 해석

"공통 기사 JSON 입력 변환·Gold 저장"을 다음으로 해석했다:

> BE/DE가 만든 **공통 기사 JSON**(BE 문서 §3)을 읽어 → **스키마 검증 · 타입 정규화 · 중복 제거**를 거쳐 → 이후 STEP 1~4가 읽는 **분석용 저장소(Gold)** 에 **멱등하게** 적재한다.

"Gold"는 Medallion 아키텍처의 "정제 완료 · 분석 준비" 레이어 의미로 받아들였다. 팀에서 다른 의미(예: Golden Set)로 쓴 것이면 이름만 바꾸면 된다. **원문 `content`는 그대로 보존**하고 보일러플레이트 제거 같은 전처리는 티켓 100에서 별도 컬럼으로 추가한다 — Gold를 두 번 만들지 않기 위해서다.

## 2. 입력

| 형태 | 지원 |
|---|---|
| `*.jsonl`, `*.ndjson` (한 줄 1건) | ✅ 기본. Kafka 덤프·HDFS 익스포트 형태 |
| `*.json` (객체 1건 또는 배열) | ✅ |
| 디렉토리 (재귀) | ✅ |
| Kafka 컨슈머 직접 연결 | ❌ 미구현. DE 인터페이스 확정 후 |
| HDFS 직접 읽기 | ❌ 미구현. 경로 확정 후 `pyarrow.fs` 또는 마운트로 |

인코딩은 `utf-8-sig`(BOM 흡수). 깨진 줄은 그 줄만 리젝트하고 파일은 계속 읽는다.

## 3. 검증 규칙 (`schema.CommonArticle`)

| 필드 | 규칙 | 위반 시 |
|---|---|---|
| 필수 문자열 9개 (`schema_version, article_id, publisher_id, publisher_name, url, title, content, category, language`) | 문자열이고 공백만이 아님 | **리젝트** |
| `source_type` | `DATASET`, `RSS`, `HTML` (`HTML` 은 DE 스키마에 맞춰 2026-08-28 추가, 티켓 100) | 리젝트 |
| `published_at` | 타임존 포함 RFC 3339. 내부 UTC 통일 | 타임존 없으면 **리젝트**, 오프셋(+09:00)은 UTC 변환 |
| 선택 필드 (`author, category_str, thumbnail_url`) | null 허용. 빈 문자열 → null 정규화 | — |
| 스키마 외 필드 | 무시 | — |
| `article_id` vs `SHA-256(publisher_id\|정규화 url)` | 비교만 함. 정규화 = 추적 파라미터(`utm_*`, `fbclid`, `gclid`)·프래그먼트 제거 (2026-08-28, 티켓 100) | 불일치해도 적재, `article_id_verified=False` 기록 |

왜 `content=""`를 리젝트하나 — 본문 추출 실패가 빈 문자열로 넘어올 수 있다. 빈 본문은 STEP 1~3 어디에도 쓸 수 없으므로 초입에서 걸러 사유를 남기는 게 낫다.
왜 타임존 없는 시각을 리젝트하나 — `published_at`이 STEP 1(48h)·STEP 3(72h) 윈도우의 기준이다. KST인지 UTC인지 모호한 값을 받아들이면 9시간 어긋나 이슈가 잘못 묶인다.

## 4. 출력 — Gold 레이아웃

```
gold/
├─ articles/
│  ├─ published_date=2026-08-20/articles.parquet   ← UTC 발행일 파티션, 파티션당 파일 1개
│  └─ published_date=2026-08-21/articles.parquet
└─ rejects/
   └─ <run_id>.jsonl                                ← {source_ref, reason, record}
```

컬럼 (`gold.GOLD_SCHEMA`): 공통 JSON 14개 필드 + 파생 5개
`published_date`(파티션 키) · `content_len` · `article_id_verified` · `ingested_at` · `source_ref`(파일:줄)

## 5. 멱등성

- 배치 안 중복: `article_id` 첫 건만 유지 (`duplicates_in_batch`로 집계)
- Gold와 중복: 기본 `on_conflict=keep` — 기존 행 유지, 새 건 건너뜀. 같은 파일을 두 번 넣어도 행 수 불변 (테스트 `test_reingest_is_idempotent`)
- `on_conflict=replace` — 재크롤링으로 수정된 기사를 반영할 때 명시적으로 사용
- 파티션 파일은 `.tmp`에 쓴 뒤 `os.replace` — 중간 실패 시 기존 파일 보존

## 6. 실행

```powershell
.\.venv\Scripts\hannun-ingest.exe --input <파일|디렉토리...> --gold-root gold [--on-conflict keep|replace] [-v]
```

출력(JSON): `files, records, valid, rejected, duplicates_in_batch, written, skipped_existing, replaced, id_mismatch, partitions, rejects_path`

샘플(`samples/articles_sample.jsonl`, 10건) 결과: `valid=6 rejected=4 duplicates_in_batch=1 written=5 id_mismatch=1`

## 7. BE 문서에서 확인한 것 / 아직 모르는 것

확인됨
- `published_at` = 기사 **발행 시각**, RFC 3339 UTC
- `article_id` = `SHA-256(publisher_id|url)`, Kafka Key와 동일 → 완전 동일 재수집은 상류에서 이미 걸러짐
- 선택 필드는 `null`(빈 문자열 아님)
- 과거 CSV는 DE가 `source_type=DATASET`으로 같은 JSON에 맞춤 → DS는 포맷 하나만 처리

미확인 (실데이터 받으면 `article_id_verified`·`content_len` 분포로 바로 검증 가능)
- [ ] `content`에 HTML 태그가 남아 있는가 → 티켓 100 범위 결정
- [ ] `article_id` 해시 전에 URL 정규화(utm 제거 등)를 하는가 → 크롤 요청 예시엔 `?utm_source=rss`가 붙어 있음
- [ ] 일 수집량 → 파티션당 파일 1개 전략이 버티는 규모인지
- [ ] DS가 HDFS에서 읽는 경로·포맷·주기 (DE)
- [ ] "Gold"라는 이름이 팀 용어와 맞는지

## 8. 나중에 바꿀 가능성

- 규모가 커지면 파티션당 파일 1개 → 배치별 파일 + 컴팩션
