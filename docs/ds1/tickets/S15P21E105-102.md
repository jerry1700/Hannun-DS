# S15P21E105-102 · 15분 증분 배정 + 전체 재군집 주기

| 항목 | 내용 |
|---|---|
| 상태 | **하이브리드 확정 (09-14, §8)** — 매시 재군집(ds_chain :05) + 15분 배정(ds_assign :20/:35/:50). 15분 전체 재군집(§7)은 주말 실측으로 철회 |
| 결과물 | `hannun.quality.assign`, CLI `hannun-assign`, 체인 `MODE=assign`, DAG `ds_chain`(매시 :05)·`ds_assign`(:20/:35/:50), 승계 통계 `retired` |
| 관련 티켓 | 89(창 재군집), 93(정형·구제 — 같은 중심·문턱 기계), 97(issueId 승계 — 15분의 전제), 118(15분 ds_input) |

## 1. 티켓 해석

운영 루프의 두 박자. **15분마다**: 새로 적재·임베딩된 대표 기사를 기존 이슈에
붙인다(배정). **주기적으로**: 48h 창 전체를 재군집해 리셋한다(이때 새 이슈 탄생·
분열·병합 반영, ID 는 티켓 97 승계로 연결). 배정은 이슈를 만들지 못하므로 재군집이
반드시 주기적으로 돌아야 한다.

## 2. 설계 실측 — 시뮬레이션 (1월 데이터)

기준 창(1/1\~1/2, 이슈 776개)을 만들고 1/3 하루치 5,209건을 "새 도착분"으로 배정,
1/1\~1/3 전체 재군집을 정답 삼아 비교 (`local/exp_incremental.py`):

| 문턱 | 배정 커버리지 | 재군집과 일치도(양쪽 배정분 ARI) |
|---|---|---|
| 0.70 | 59.3% | 0.356 |
| 0.80 | 32.7% | 0.347 |
| **0.85** | **16.1%** | **0.789** |
| 0.90 | 5.7% | 0.886 |

읽는 법:

1. **문턱 0.85 채택** — 0.80 이하는 붙는 양은 많지만 재군집과 다른(=틀린) 이슈에
   붙는 비율이 압도적(일치 0.35). 0.85부터 일치 0.79로 뛴다. 구제(93)와 같은 값이라
   "이슈 중심 유사도 0.85"라는 단일 규칙이 된다.
2. **배정은 보조, 재군집이 본체** — 새 기사의 84%는 기준 창에 붙을 곳이 없다
   (대부분 새로 태어나는 이슈 소속). 1/3 기사 중 재군집 기준 81%가 이슈에 들어가는데
   그 대부분이 신규 이슈다. 뉴스의 회전이 그만큼 빠르다(분출 실측과 일치).
3. **재군집 주기 = 새 이슈 노출 지연** → 짧을수록 좋고, 비용이 허락한다:
   창 재군집이 1분 미만(29,497건 49초 실측). **권고: 1시간 주기 재군집 + 15분 배정.**
   15분마다 재군집하지 않는 이유는 비용이 아니라 안정성 — 라벨이 96번/일 리셋되면
   승계(97) 부하와 서비스 이슈 목록 출렁임이 커진다.

## 3. 구조

```
(15분) 새 embedding 행 중 issue 에 없는 기사
  → 비정형 이슈 중심과 코사인 ≥ 0.85 → 그 이슈로 임시 배정, 아니면 -1
  → issue 파티션에 추가(규모 갱신), 이어서 hannun-quality 재실행
(1시간) hannun-cluster 로 창 전체 재군집 → 임시 배정 포함 전부 리셋 → 승계(97)
```

- 배정 대상에서 정형 이슈 제외 — 구제(93)와 같은 이유(오염 방지). 정형 판별은
  현재 issue 테이블에서 즉석 계산하므로 issue_quality 없이도 동작
- 배정 행은 "다음 재군집까지의 임시 판정" — 재군집이 파티션을 통째로 덮어쓰며 소멸
- 모듈은 `hannun.quality` 에 둔다 — 구제와 같은 중심·문턱 기계를 재사용하고,
  clustering ← quality 의존 방향을 유지(역방향이면 순환)

## 7. 15분 전체 재군집으로 확정 (2026-09-11)

설계 당시 "15분 배정 + 주기 재군집"의 두 박자였던 것을 **15분 전체 재군집
하나**로 단순화해 가동했다. 팀 합의(서비스 품질 — 이슈 반영을 실시간에 가깝게)
+ 전제 두 개가 그 사이에 갖춰졌기 때문:

1. **ds_input 15분 내려주기**(118, article_ingest) — 재료가 15분마다 도착
2. **자기-승계**(97 §4.6) — 같은 창 재군집에도 이슈 ID 유지 (재군집을 자주
   못 돌리던 유일한 이유가 이것이었다)

| 결정 | 이유 |
|---|---|
| ds_chain 에 `*/15` 스케줄 | 재군집이 본체(새 기사 84%는 붙을 이슈가 없음 — §2 실측). 배정 루프는 예비로 보존 |
| retries=0 | 15분 주기에서는 다음 실행이 자연 재시도 — 별도 재시도는 flock 경합 소음만 만든다 |
| execution_timeout 30분 | 걸린 실행이 뒤 실행들을 오래 막지 않게 (max_active_runs=1 직렬화) |
| ds_daily 트리거와 당분간 공존 | 겹쳐도 직렬화+멱등으로 무해. 트리거 정리·gold 병합 주기는 DE 협의 항목 |

가동 후 관찰 항목: 실행 소요 시간(증분이면 2~3분 추정, 15분 예산 내), 서버
CPU(article_ingest 스파크와 경합), inherited/created/splits 추이(자기-승계 실전).
남은 것: DE 의 gold 병합·발행 주기 정렬(그 전까지 BE 반영은 하루 1회 그대로),
발행 자체는 DS2 관점 라벨(120/30) 대기.

## 8. 하이브리드로 재확정 (2026-09-14) — §7 의 15분 전체 재군집을 주말 실측으로 철회

15분 전체 재군집을 금\~월 66시간(262회) 돌려 본 결과:

| 지표 | 실측 | 뜻 |
|---|---|---|
| 실행 | 262/283 슬롯 success, 실패 0, 소요 6.7\~11분 | 주기 자체는 안정 |
| inherited | 같은 창 재실행마다 247→248→249 | 자기-승계 작동 — 큰 이슈 ID 는 유지 |
| **created / splits** | **실행당 36\~57 / 11\~32** | 15분 새 기사 \~80건인데 이슈 40\~50개가 새 ID — **경계 출렁임** |
| DE article_ingest | 2.5분 → 3.5분 | 같은 :15:00 에 동시 출발해 CPU 경합 + 우리는 15분 묵은 입력을 읽음 |

원인: UMAP+HDBSCAN 을 매번 처음부터 다시 그리면 기사 80건 추가에도 지도가 미세하게
재배열되고 경계의 작은 이슈가 쪼개졌다 붙었다 한다. 하루 96회 × \~45 = **\~4,000 ID/일**
발급, 진짜 새 이슈(400\~700/일)의 6배 — 발행이 붙으면 이슈가 나타났다 사라지는 것이
그대로 보인다. §2 에 적어 둔 "15분 재군집을 피하는 이유 = 출렁임"이 그대로 실현된 것.
자기-승계는 'ID 리셋'을 고쳤지만 '경계 출렁임'은 못 고친다.

**결정: §1 원안의 하이브리드로 복귀** — 검증된 부품(배정 0.85, 재군집 대비 일치 0.789)
조합이라 위험 최소.

| 결정 | 이유 |
|---|---|
| `ds_chain` 매시 :05 전체 재군집 | 새 이슈 탄생·분열·병합은 시간당 1회 → 출렁임 4배↓. :05 = article_ingest(:00\~:03) 직후라 갓 내려온 입력 + 경합 회피 |
| `ds_assign` :20/:35/:50 배정 (새 DAG, 같은 이미지, `MODE=assign`) | 기존 이슈를 건드리지 않고 새 기사만 붙임 — 출렁임 0. 못 붙는 \~84%는 정시까지 대기 |
| 배정 뒤에도 승계 실행 | 붙은 기사가 registry(DE 피드 멤버십)에 들어가야 15분 반영이 실제가 됨 |
| 이슈 표 없으면 재군집 폴백 | 자정 직후 첫 창 등 — 배정은 이슈를 만들지 못하므로 |
| flock `-w 240` (둘이 같은 잠금) | 재군집이 길어 겹치면 배정이 4분 기다렸다 양보 — 빨간불 소음 최소화 |
| 승계 통계 `retired` 추가 | 사라진 이슈 수 — 출렁임을 매 실행 수치로 감시 |

검증(로컬 1월, 스크래치 루트): 1/2 창 이슈 표에 1/3 임베딩 5,209건 배정 → **608건
붙음**(§4 스모크 662 와 같은 규모) → 승계: inherited 509/509, created 0, splits 0,
retired 0, **registry +608 = 배정 건수와 정확히 일치**. 테스트 314 통과(신규: retired).

대안으로 검토한 것: (B) UMAP 을 하루 1회만 학습하고 15분엔 새 점만 투영(transform) —
근본 해결 + 속도 개선이지만 2\~3일 + 투영 품질 검증 필요 → MVP 뒤 고도화. (C) 쪼개진
작은 조각에 부모 ID 유지 — 피드 병합 처리가 필요하고 출렁임 자체는 남음.

### 8.1 첫 하이브리드 사이클 실측과 관찰 도구 보정 (2026-09-14 오전)

| 실행 | 소요 | created / splits |
|---|---|---|
| 09:53 배정 | 6.5분 | **0 / 0** — 설계대로 출렁임 없음 |
| 10:05 재군집 | 7분 | 49 / 26 — 시간당 1회로 한정됨 |

**병목은 군집화가 아니다**: 재군집을 빼도 30초밖에 안 줄어 6분의 대부분이 다른
단계(적재 3일 재처리·전처리·중복 제거·임베딩 모델 로딩·DS2 내보내기 중)에 있다.
어느 단계인지 보이도록 체인 스크립트에 `step` 래퍼를 넣어 단계마다
`[chain] step <이름> <초>s rc=<코드>` 를 남긴다 — 다음 사이클 몇 번이면 병목 단계가
드러나고, 그 단계만 증분화하면 배정 실행을 1\~2분대로 줄일 수 있다(15분 주기 CPU
점유 절반 이하). 종료 코드를 그대로 돌려줘 `step assign … || step cluster …` 폴백과
실패 시 체인 중단(set -e)이 그대로 동작한다(bash 로 확인).

`retired` 정의 보정: 첫 실측이 배정 실행에서도 159 로 나왔는데 이는 출렁임이 아니라
창 전진 때 자연 소멸한 어제 이슈가 재실행마다 반복 집계된 것. "바로 직전"(자기-승계
실행이면 같은 창의 직전 실행, 첫 실행이면 직전 창) 대비로 바꿔 배정 실행은 0,
재군집 실행은 그 시간의 출렁임(\~20\~30)만 찍히게 했다.
