## 1. 티켓 해석

코드 리뷰(2026-09-22)가 `embed()` 에서 두 결함을 짚었다. 둘 다 코드를 대조해 맞는 것으로 확인했다.

| 결함 | 어디서 | 결과 |
|---|---|---|
| 나중에 중복으로 접힌 기사의 벡터가 남는다 | 기존 행을 `rows = existing` 으로 전부 보존 — 이번 실행에 folded 가 된 기사도 함께 | 같은 글이 벡터 공간에 둘 — HDBSCAN 밀도 과대평가, 이슈 크기·대표·구제 왜곡 |
| 본문이 바뀌어도 같은 모델이면 재사용 | 재사용 조건이 article_id·model 뿐 | 재크롤링 `replace` 나 정제 규칙 개정 뒤에도 옛 본문의 벡터로 군집 — Gold·DS2 는 새 본문, 벡터는 옛 본문 |

늦게 들어온 기사가 대표를 밀어내는 일은 DE 가 최근 3일을 매번 다시 내려주는 구조에서
실제로 일어난다(발행은 앞서지만 수집은 늦은 기사). 규칙 개정은 119 에서 실제로 했다 —
그때는 창을 통째로 재처리해 벡터도 새로 만들었지만, 코드가 그것을 보장한 것은 아니었다.

## 2. 결정

| 결정 | 이유 |
|---|---|
| 재사용 조건 = 인코더 입력 해시 `input_sha1` 동일 | 해시는 `passage_prefix + build_input(title, 정제본, body_chars)` — 제목·정제본·접두어·본문 길이 중 무엇이 바뀌어도 벡터가 바뀌어야 하므로 그 전부를 넣는다. 규칙 버전을 따로 저장하지 않는 이유: 규칙이 바뀌어도 이 기사의 정제본이 같으면 다시 인코딩할 이유가 없다 |
| 기존 행 중 이번에 접힌 기사·다른 모델·Gold 에서 사라진 기사는 버린다 | 남길 행은 "지금 대표이고 입력이 같은 것"만. 옛 코드가 다른 모델 행을 버리던 것과 같은 자리에서 접힌 기사도 함께 정리 |
| 옛 파티션(`input_sha1` 컬럼 없음)은 해시가 None 이라 전부 재인코딩 | 서명 캐시(123)·고정 지도(128)와 같은 원칙 — 조용히 옛 값을 쓰지 않는다. 첫 실행 한 번, 창 8천 건이면 EC2 에서 1~2분 |
| `read_table` 은 컬럼이 다른 파티션을 `promote_options="default"` 로 합친다 | 창 밖의 옛 파티션과 새 파티션이 섞여 읽히는 스크립트(시뮬레이션·채점)가 깨지지 않게. 없는 컬럼은 null |
| 통계 `reencoded`·`removed` 추가 | 체인 로그에서 "본문이 바뀐 기사 몇 건, 접혀서 지운 벡터 몇 건"이 보인다 |

## 3. 산출 컬럼 변경 (`gold/embedding/published_date=…/embedding.parquet`)

| 컬럼 | 뜻 |
|---|---|
| `input_sha1` (신규) | 인코더 입력 문자열의 SHA-1. 같으면 재사용, 다르면 재인코딩. 옛 파티션에는 없다(null) |

나머지 컬럼(`article_id`·`publisher_id`·`published_date`·`vector`·`dim`·`model`·`encoded_at`)은 그대로.

## 4. 검증

- 테스트 +4: 늦게 접힌 기사의 벡터 제거(`removed`), `replace` 로 본문이 바뀐 기사 재인코딩(`reencoded`, 벡터 변화), `input_sha1` 없는 옛 파티션 전부 재인코딩, 옛·새 스키마 파티션 섞어 읽기. 기존 6개 그대로 통과
- 배포 뒤 첫 `step embed` 는 창 전체(수천 건) 재인코딩으로 1\~2분, 그 뒤부터 종전 20\~30초. 통계
  `"reencoded"` 가 첫 실행에 창 크기, 이후엔 재크롤링 건수 안팎이면 정상. `"removed"` 는 늦게 접힌 기사 수
