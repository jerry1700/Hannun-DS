## 1. 티켓 해석

하이브리드 첫 사이클(09-14)의 단계별 소요(102 §8.1 의 step 로그)로 배정 실행 6.5분의
행방이 드러났다:

| 단계 | 소요 | 비중 |
|---|---|---|
| export (DS2 분석 내보내기) | 232초 | 60% |
| dedup (중복 제거) | 104초 | 27% |
| embed | 32초 | 8% |
| 나머지 8단계 | \~20초 | 5% |

15분마다 이슈 \~300개를 **전부** DS2 함수로 다시 분석하는데(이슈당 0.8초), 배정 실행에서
구성원이 바뀌는 이슈는 수십 개뿐이다. 중복 제거도 48h 창의 LSH 인덱스를 매번 처음부터
다시 만든다. 둘을 증분화해 배정 실행을 1.5분대로 — 15분 주기 서버 점유 43%→10%대,
DE article_ingest 경합(2.5→3.5분) 해소.

## 2. 1단계 — 내보내기 재사용 (`--reuse-unchanged`)

| 결정 | 이유 |
|---|---|
| 이전 실행이 남긴 **오늘 파일 자체**를 캐시로 | 새 저장소·스키마 없이 clusterId 별 원문 줄·링크 집합·대표 제목·카테고리를 읽으면 충분 |
| 재사용 조건 = 링크 집합·대표 제목·카테고리 **전부 동일** | DS2 분석은 입력이 같으면 출력이 같다(결정적) — 재사용은 근사가 아니라 바이트 동일 결과. 기사 하나만 붙어도 재분석 |
| **배정 실행에만** 적용, 재군집 실행은 전량 재분석 | DS2 코드가 바뀌어(예: 관점 라벨 머지 후 이미지 재빌드) 옛 분석이 남는 시간을 최대 1시간으로 한정 |
| 재사용 줄의 `clusteredAt` 은 이전 값 유지 | 분석 시각이라는 의미에 더 맞고, DE 는 clusterId 별 최신만 고르므로 영향 없음 |
| 통계 `reused_issues` 추가 | 매 실행 재사용률이 로그에 남는다 |

DS2 소유 스크립트라 MR 리뷰어는 구윤지. 스크립트에 `load_previous`·`unchanged` 를
순수 함수로 분리해 테스트 3개(인덱싱·재사용 조건·깨진 줄 무시).

## 5. 2단계 — 중복 제거 증분화 (2026-09-14 오후)

프로파일(로컬 2023 이틀 창, 후보 40만 쌍)로 비중을 재고 운영 창(후보 1.3만 쌍)에
환산하면 서명 \~50초·인덱스 \~17초·검증 \~33초 = 실측 104초와 일치. 두 축을 손봤다.

| 결정 | 이유 |
|---|---|
| MinHash 서명을 `dedup_sig/` 테이블에 저장, 새 기사만 계산 | 기사 8천 건 × 4-gram × 128해시가 매 실행 반복되던 부분. 정제본 sha1 이 다르면 무효(전처리 규칙 개정 대응) |
| 서명 설정(shingle_size·num_perm)과 **datasketch 해시 방식(scheme)**도 저장·비교 | 라이브러리 판이 바뀌어 방식이 달라지면 옛 서명이 조용히 틀린 후보를 만든다 — 실제로 datasketch 2.x 가 되살릴 때 scheme 을 요구해 드러난 위험 |
| MinHash seed 도 명시하고 유효 조건에 넣음 (2026-09-14, 티켓 124) | 순열은 seed 로 결정되는데 라이브러리 기본값(1)에 조용히 기대고 있었다. 캐시 API 는 인자 5개 대신 `CandidateConfig` 하나를 받고, 컬럼 구성이 다른 옛 파티션은 읽는 쪽이 버린다 |
| 검증 코사인을 쌍별 호출 대신 덩어리 내적으로 | TF-IDF 행은 L2 정규화돼 있어 내적 = 코사인. 2만 쌍 단위로 잘라 후보 40만 쌍에서도 메모리 안전 |
| containment 의 4-gram 집합을 기사당 한 번만 | 기각 쌍 1.2만 개마다 두 기사의 집합을 다시 만들던 것(2.5만 회) 제거 |
| 창 전체 재판정은 그대로 | 인덱스·검증은 새 기사와 옛 기사의 쌍을 봐야 하므로 — 증분화는 "계산 재사용"이지 "범위 축소"가 아니다. 판정 결과는 캐시 없이 돌린 것과 동일 |

|---|---|

LSH 인덱스 재구성(\~10초)과 적재. 운영 창 예상: **104초 → 25초 안팎**. 배정 실행 전체는
6.5분 → \~1.5분(export 32초 + dedup 25초 + 임베딩 32초 + 나머지 20초).

## 7. 배포·확인

머지 후 EC2 `git pull` + `docker build`. 첫 실행은 서명을 전부 계산해 종전과 비슷하고
**두 번째 실행부터** `step dedup` 이 20초대여야 한다. dedup 통계의
`signatures_cached/computed` 에서 computed 가 15분치 새 기사 수와 비슷하면 정상.
`~/gold/dedup_sig/` 는 발행일 파티션이라 gold 와 함께 자란다(하루 \~4MB).

### 7.1 운영 실측 (2026-09-14 저녁)

| 실행 | `step dedup` |
|---|---|
| 배포 직후(캐시 없음) | 114초 |
| 이후 배정 실행 | 52\~57초 (`signatures cached/computed` 3,636/116) |

예상(25초 안팎)에 못 미쳤다. 이유는 둘 — EC2(t3.xlarge) 단일 코어가 로컬의 절반
속도이고, 남는 시간의 대부분이 서명이 아니라 매 실행 다시 만드는 LSH 인덱스(8천 건
삽입 + Ensemble 파티션)와 containment 검증의 shingle 집합 생성이다. 판정은 캐시 없이
돌린 것과 동일(접힘 수 일치). MVP 에서는 이 수준으로 수용한다 — 배정 실행 전체가
6.5분에서 \~2분으로 줄어 15분 주기 안에 넉넉히 든다. 더 줄이려면 LSH 인덱스를 피클로
저장해 새 기사만 삽입하는 길이 남아 있다(고도화 카드).
