## 1. 티켓 해석

하이브리드 첫 사이클(09-14)의 단계별 소요(102 §8.1 의 step 로그)로 배정 실행 6.5분의
행방이 드러났다:

| 단계 | 소요 | 비중 |
|---|---|---|
| export (DS2 분석 내보내기) | 232초 | 60% |
| dedup (중복 제거) | 104초 | 27% |
| embed | 32초 | 8% |
| 나머지 8단계 | \~20초 | 5% |

15분마다 이슈 \~300개를 **전부** DS2 함수로 다시 분석하는데(이슈당 0.8초), 배정 실행에서
구성원이 바뀌는 이슈는 수십 개뿐이다. 중복 제거도 48h 창의 LSH 인덱스를 매번 처음부터
다시 만든다. 둘을 증분화해 배정 실행을 1.5분대로 — 15분 주기 서버 점유 43%→10%대,
DE article_ingest 경합(2.5→3.5분) 해소.

## 2. 1단계 — 내보내기 재사용 (`--reuse-unchanged`)

| 결정 | 이유 |
|---|---|
| 이전 실행이 남긴 **오늘 파일 자체**를 캐시로 | 새 저장소·스키마 없이 clusterId 별 원문 줄·링크 집합·대표 제목·카테고리를 읽으면 충분 |

| 처음엔 **배정 실행에만** 적용, 재군집 실행은 전량 재분석 | DS2 코드가 바뀌어(예: 관점 라벨 머지 후 이미지 재빌드) 옛 분석이 남는 시간을 최대 1시간으로 한정 |
| → **두 모드 모두 재사용** (2026-09-15, 티켓 102 §8.2) | 이슈 714개에서 재군집 export 가 837초가 되어 :20 배정을 밀어냈다. 하루 첫 실행(자정 KST, 그날 파일 없음)이 자연히 전량 재분석이라 시간 조건 없이 DS2 코드 변경은 다음 날 자정에 반영 |
| 재사용 줄의 `clusteredAt` 은 이전 값 유지 | 분석 시각이라는 의미에 더 맞고, DE 는 clusterId 별 최신만 고르므로 영향 없음 |
| 통계 `reused_issues` 추가 | 매 실행 재사용률이 로그에 남는다 |

DS2 소유 스크립트라 MR 리뷰어는 구윤지. 스크립트에 `load_previous`·`unchanged` 를
순수 함수로 분리해 테스트 3개(인덱싱·재사용 조건·깨진 줄 무시).

## 5. 2단계 — 중복 제거 증분화 (2026-09-14 오후)

프로파일(로컬 2023 이틀 창, 후보 40만 쌍)로 비중을 재고 운영 창(후보 1.3만 쌍)에
환산하면 서명 \~50초·인덱스 \~17초·검증 \~33초 = 실측 104초와 일치. 두 축을 손봤다.

| 결정 | 이유 |
|---|---|
| MinHash 서명을 `dedup_sig/` 테이블에 저장, 새 기사만 계산 | 기사 8천 건 × 4-gram × 128해시가 매 실행 반복되던 부분. 정제본 sha1 이 다르면 무효(전처리 규칙 개정 대응) |
| 서명 설정(shingle_size·num_perm)과 **datasketch 해시 방식(scheme)**도 저장·비교 | 라이브러리 판이 바뀌어 방식이 달라지면 옛 서명이 조용히 틀린 후보를 만든다 — 실제로 datasketch 2.x 가 되살릴 때 scheme 을 요구해 드러난 위험 |
| MinHash seed 도 명시하고 유효 조건에 넣음 (2026-09-14, 티켓 124) | 순열은 seed 로 결정되는데 라이브러리 기본값(1)에 조용히 기대고 있었다. 캐시 API 는 인자 5개 대신 `CandidateConfig` 하나를 받고, 컬럼 구성이 다른 옛 파티션은 읽는 쪽이 버린다 |
| 검증 코사인을 쌍별 호출 대신 덩어리 내적으로 | TF-IDF 행은 L2 정규화돼 있어 내적 = 코사인. 2만 쌍 단위로 잘라 후보 40만 쌍에서도 메모리 안전 |
| containment 의 4-gram 집합을 기사당 한 번만 | 기각 쌍 1.2만 개마다 두 기사의 집합을 다시 만들던 것(2.5만 회) 제거 |
| 창 전체 재판정은 그대로 | 인덱스·검증은 새 기사와 옛 기사의 쌍을 봐야 하므로 — 증분화는 "계산 재사용"이지 "범위 축소"가 아니다. 판정 결과는 캐시 없이 돌린 것과 동일 |

## 7. 배포·확인

머지 후 EC2 `git pull` + `docker build`. 첫 실행은 서명을 전부 계산해 종전과 비슷하고
**두 번째 실행부터** `step dedup` 이 20초대여야 한다. dedup 통계의
`signatures_cached/computed` 에서 computed 가 15분치 새 기사 수와 비슷하면 정상.
`~/gold/dedup_sig/` 는 발행일 파티션이라 gold 와 함께 자란다(하루 \~4MB).

### 7.1 운영 실측 (2026-09-14 저녁)

| 실행 | `step dedup` |
|---|---|
| 배포 직후(캐시 없음) | 114초 |
| 이후 배정 실행 | 52\~57초 (`signatures cached/computed` 3,636/116) |

예상(25초 안팎)에 못 미쳤다. 이유는 둘 — EC2(t3.xlarge) 단일 코어가 로컬의 절반

## 8. 3단계 — export 병렬화 (2026-09-17)

### 8.1 왜 다시 export 인가

DS2 관점 라벨(120)이 9/17 머지되며 세부 견해 군집이 문장 임베딩 모델(e5-small, 우리 임베딩과
같은 모델)을 쓰기 시작했다. 로컬 1/2 창 509 이슈 전량 분석이 206초 → **645초**(이슈당 0.4 →
1.3초, 3.1배). EC2 배정 실행 export 도 40초대에서 52\~116초로 늘었다. 다만 그날 밤 23:05
재군집의 export 는 **879초**로 라벨 머지 전(837\~1,010초)과 같은 수준 — 로컬의 3배 증가가 EC2
재군집에는 그대로 나타나지 않았다(이슈 크기 분포 차이로 본다). 그래도 재군집 15분은 :20 배정을
3분 기다리게 하고 DE 의 :27 피드 생성과 겹친다. 재사용으로는 더 못 줄인다(재군집은 구성원이
실제로 바뀐다) — 남은 축은 코어를 쓰는 것이다. 이슈 분석은 서로 독립인 순수 CPU 작업.

### 8.2 결정

| 결정 | 이유 |
|---|---|
| `--workers N` — 1회차에 재사용/분석 대상을 가르고, 분석 입력만 프로세스 풀 `pool.map` 으로 | 출력 순서(issue_summary 순)와 줄 내용은 순차와 같다. 재사용 줄은 풀에 보내지 않는다 |
| 프로세스마다 모델을 올리고 `OMP_NUM_THREADS=1` | 워커 3개가 각각 4 스레드를 쓰면 4 vCPU 에서 서로 빼앗는다. 모델 로드는 워커당 한 번(\~5초) |
| `spawn` | 부모가 pandas·pyarrow 스레드를 이미 띄운 뒤라 fork 는 교착 위험. Windows 테스트에는 fork 가 없다 |
| 체인 기본 `EXPORT_WORKERS=3` | t3.xlarge 4 vCPU 중 하나는 DE article_ingest·Airflow 몫으로 남긴다 |
| `--workers 1` 이 기본 | 스크립트 단독 실행·테스트는 종전과 같은 순차 경로 |

DS2 소유 스크립트라 리뷰어는 구윤지. DS2 의 메시지 조립 코드는 `issue_input`·`build_message`
함수로 옮겼을 뿐 내용은 그대로다. 통계에 `analyzed_issues`·`workers` 추가.

### 8.4 어디에 시간이 가는가 — DS2 에 전달할 프로파일 (로컬 1/2 창, 실제 이슈 39개 cProfile)

| 구간 | 비중 | 무엇 |
|---|---|---|
| `generate_fact_summary` → `select_common_facts` → `_same_fact_by_scores` | **75%** | 공통 사실 추출의 문장 쌍 비교. 39 이슈에서 28만 호출 — 문장 수의 제곱 |
| `_cluster_many_articles` → `_embed_texts` (E5 문장 임베딩) | 13% | 세부 견해 군집. 새로 붙은 모델 비용은 이쪽이지만 주범은 아니다 |
| stance 분류·키워드·나머지 | 12% | |

이슈 크기 분포(502개): 기사 수 중위 6, 상위 10% 15, 최대 75. **기사 75건짜리 이슈 하나가 78초**
(69건 12.7초, 41건 14.4초) — 제곱 비용이라 큰 이슈 한둘이 전체를 끌고 간다. 병렬화는 그 한
이슈보다 짧아질 수 없다. 근본 개선은 DS2 몫: 이슈당 비교할 문장 수에 상한을 두거나(기사
n 건 × 문장 k 개 캡), 쌍 비교를 TF-IDF 행렬 연산으로 바꾸는 것. 이 표를 구윤지에게 전달한다.
