# Git 컨벤션

브랜치 구조와 이름 규칙은 팀 공통이고, 커밋 메시지와 MR 규칙은 데이터 파트에서 정한 것이다.

## 브랜치 구조

```
master
└── develop
    ├── front/master → front/dev → front/feat, front/fix, front/refactor
    ├── back/master  → back/dev  → back/feat,  back/fix,  back/refactor
    └── data/master  → data/dev  → data/feat,  data/fix,  data/refactor
```

우리 작업은 전부 `data/` 아래에서 한다. `data/dev` 와 `data/master` 에는 직접 푸시하지 않는다.

`data/` 안은 `de/`(DE)와 `ds/`(DS1·DS2 공용)로 나뉜다. `ds/` 안에서는 모듈 단위로
소유자가 있고, 개인 문서는 `ds/docs/ds1/`, `ds/docs/ds2/` 에 둔다. 자기 것은 자유롭게
고치되, 다른 사람 모듈이나 공통 파일(`data/README.md`, `data/docs/`, `ds/README.md`,
`ds/pyproject.toml`)을 건드리는 MR 은 그 소유자를 리뷰어로 넣는다.

## 브랜치 이름

```
data/<유형>/<지라 키>-<짧은-이름>

data/feat/S15P21E105-99-json-gold
data/fix/S15P21E105-104-golden-score
data/refactor/S15P21E105-101-packaging
```

영문 소문자와 하이픈만 쓴다. 이름만 보고 무슨 작업인지 알 수 있어야 하고, 브랜치
하나에서는 한 티켓만 처리한다.

지라 키(대문자)가 브랜치 이름에 들어가면 깃랩이 지라와 연동한다. 브랜치를 만들면
티켓이 자동으로 "진행 중"이 되고, MR 이 머지되면 "완료"가 된다. 시작 브랜치는
항상 `data/dev`.

## 작업 유형

| 유형 | 쓰는 때 |
|---|---|
| feat | 기능 추가, 요구사항에 맞춘 기능 수정 |
| fix | 버그 수정 |
| refactor | 동작이 바뀌지 않는 구조 변경 |
| test | 테스트 추가·수정 |
| docs | 문서·주석 수정 |
| style | 포맷팅, 이름 바꾸기 |
| chore | 설정 파일, 의존성, .gitignore 등 |
| build | 빌드·패키징 |
| deploy | 배포 설정 |
| release | 버전 릴리즈 |

브랜치 유형과 커밋 유형은 같은 단어를 쓴다.

## 커밋 메시지

```
<유형>: <제목> (<지라 키>)

<본문 — 왜 이 변경인지. 무엇을 바꿨는지는 diff 가 말한다>
```

```
feat: 공통 기사 JSON 검증과 Gold parquet 적재 (S15P21E105-99)

BE 가 Kafka 로 내보내는 공통 기사 JSON 을 파일로 받아 검증하고
published_date 파티션으로 쌓는다. 같은 article_id 는 한 번만 들어가므로
같은 파일을 다시 넣어도 결과가 바뀌지 않는다.
```

- 팀 공통 형식의 `(<area>)` 는 데이터 파트에서 생략한다 — 브랜치 접두어
  `data/` 로 이미 구분되고, 파트 초기부터의 커밋들과 형식을 유지한다.
  지라 키를 제목 끝에 붙이는 것은 데이터 파트 추가 규칙
- 제목은 한글, 50자 안, 마침표 없이. "수정"·"변경"처럼 모호한 표현만 단독으로
  쓰지 않는다. 본문은 있어도 없어도 되지만, 왜 그렇게 했는지 나중에 물을 만한
  결정이 있으면 적는다

커밋 하나는 논리 단위 하나다 — 기능 구현↔리팩터링↔테스트↔배포 설정은 커밋을
분리한다(기능 검증에 반드시 필요한 테스트는 기능과 같은 커밋에 가능). "wip",
"수정" 같은 커밋은 MR 올리기 전에 정리한다. 다음은 커밋에 넣지 않는다.

- `gold/` 같이 코드가 만드는 파일
- 실제 기사 데이터. 샘플은 `scripts/` 로 생성해 `samples/` 에만
- 모델 가중치, `.venv`, 에디터 설정

## Merge Request

작업이 끝나면 `data/feat/*` 에서 `data/dev` 로 MR 을 올린다. **타겟 브랜치를
반드시 확인한다** — GitLab 기본값이 `develop` 으로 잡힌다. develop·master 타겟
MR 은 버전 릴리스 때만 만든다.

- 제목은 커밋과 같은 형식: `<유형>: <제목> (<지라 키>)`.
  머지 커밋 메시지가 MR 제목으로 만들어지므로 제목이 곧 브랜치 히스토리다.
  GitLab 이 첫 커밋 메시지로 자동 채우니, 지라 키가 브랜치의 티켓과 같은지
  확인한다 — 다른 키가 들어가면 머지 때 그 티켓이 완료 처리된다(TS-008)
- 설명 첫 줄에 `Closes S15P21E105-99` — 이 줄이 있어야 머지 때 티켓이 자동 완료된다
- 이어서 세 항목: **무엇**(한두 문장) / **왜·변경점**(리뷰어가 diff 만 봐선 알 수
  없는 결정과 근거) / **검증**(`pytest`·`flake8` 결과, 수동 확인 방법)
- 리뷰어 한 명 이상 지정. 본인이 머지하지 않는다
- 머지 후 작업 브랜치는 지운다

`data/dev` → `data/master` → `develop` 은 파트 단위로 안정됐을 때 올린다.

## 새 작업 이슈 만들 때

- 유형 "작업", 상위 항목은 소속 에픽, 담당자는 본인
- "연결된 업무 항목"에서 relates to 로 소속 스토리 연결
- 이슈를 만들면 사지한에게 알린다
